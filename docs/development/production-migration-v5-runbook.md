# Production migration V5 runbook

This runbook describes the owner-authorized manual release path for the six-migration `active-energy-unified-v2` release. A merge or green CI does not deploy this incompatible-schema release. Every production workflow requires a `main` dispatch for the exact current SHA, green CI for that SHA, trusted owner identity `126446430`, and its explicit confirmation input.

## Compatibility decision

The old app at base `e84a627864fe86097596b921d4a2b27dd0f5798e` generates Prisma upserts using `profileId_date` for both `ExperimentalSkeletalMuscleDeltaShadow` and `ExperimentalCessationDetrainingShadow`. The Relative Muscle migrations drop those unique indexes and replace them with episode-aware `(profileId, modelEpisodeId, date) NULLS NOT DISTINCT` uniqueness. The old app therefore cannot safely run against the migrated schema. This release uses a maintenance cutover; it does not add a compatibility index or change episode semantics.

Before DDL, the preflight workflow must:

1. Publish the exact 503 maintenance route and confirm the public endpoint serves it.
2. While the healthy prior app container is still inspectable, capture its immutable image/container/runtime identity and take a fixed read-only schema/history compatibility snapshot. That snapshot is explicitly non-admissible (`ready: false`) and does not claim writer drain or authorize migration.
3. Disable automatic restart, stop and remove the old app container. An exited container is insufficient because it could be restarted against the incompatible schema.
4. Only after app removal, confirm no other client container remains on `bodycast-backend-prod`, PostgreSQL has no published port and is attached only to that internal network, and `gymbeam-caddy` validates the maintenance route. The full read-only preflight then records DB identity/history/schema/locks and the strict writer-drain evidence. Unknown containers, external DB routes, NAT/proxy ambiguity, missing evidence, or a still-present app container fail closed.
5. Keep Caddy maintenance enabled until the exact authorized release SHA is healthy, V3 postflight passes, V4 activation/replay is explicitly completed, and V4 currentness/coverage checks pass.

If the migration's final live guard fails before `ddl-started` and a later preflight is blocked by the durable prior-app capture, do not remove that capture or reuse the old backup. The preflight workflow supports one narrowly verified resume: the owner supplies the successful source-preflight run, the exact owner-dispatched migration run, and the retry that stopped at the existing-capture guard. The authorization job verifies those original run attempts, the exact known final-guard import error, source artifacts, and that no other production mutation workflow intervened. On the host, the resume still requires current `main`, confirmed maintenance, no marker, no app container, complete writer drain, the pinned previous image, and exact live DB identity/history/schema compatibility with the saved capture. It only rebinds that capture; the resumed run must create a fresh encrypted backup and pass a fresh isolated restore/migration rehearsal before DDL authorization. Any other failure or mismatch remains blocked for operator review.

The separate forward-resume mode admits only the reviewed historical failure `38022978032`, with authenticated raw GitHub job logs, exact source guard bytes, and the historical owner-signed context proving rejection before Prisma spawn. It inventories every repository run since that source with complete pagination and a stable repeated snapshot. Intervening production runs are admitted only when the pinned owner failed the exact authorization step and the production job never started; retries are discovered dynamically, without an ID allowlist. The read-only checkout diagnostic is classified separately only if its workflow and fixed inspector dependencies match the audited current-main blobs and its complete owner job/step sequence succeeds. Unknown, incomplete, rerun, stale, or mutation evidence blocks continuation. History and source proof are rechecked before production access.

Ordinary and forward capture resumes use the same closed receipt schema v2. The forward receipt additionally binds the failed run/attempt/SHA, no-spawn proof, live marker digest, source owner-signed capture digest, and current capture run/attempt. This permits no marker clearing or DDL by itself: a fresh current-live encrypted backup, isolated restore and six-migration rehearsal, then separate fresh signed owner migration authorization are still required.

The preflight SQL records the named `bodycast-production-preflight` observer PID and every other PostgreSQL client backend without relying on `client_addr` for identity. Any other client blocks, including a backend with an empty/unknown application name. Host topology evidence is captured from Docker/Caddy and included in the preflight report. The report, restore rehearsal, artifact digests, writer drain, and exact release identity are bound into the Ed25519 owner authorization. Immediately before DDL, the fixed SSH migration script rechecks canonical main, committed migration bytes, live database identity, backup freshness, and PostgreSQL client inventory. Reconnected or unclassified clients block DDL.

The currently reviewed production topology contract is the local Compose stack in `docker-compose.prod.yml`: `bodycast-db-prod` is reachable only on the internal `bodycast-backend-prod` network; the app uses that network and `gymbeam-internal`; Caddy is `gymbeam-caddy`; and the host route is `bodycast.caddy`. A different topology, database proxy, published port, or NAT path is unsupported by this evidence contract and must remain blocked until its client identity and drain proof are reviewed and implemented. Do not waive the topology check or treat `pg_stat_activity.client_addr` as sufficient evidence.

## Owner-authorized execution and order

1. Review canonical `main`, exact release SHA, successful CI for that SHA, and the six hashes above.
2. Dispatch **Production migration preflight and encrypted backup** from `main` with that SHA, manifest `active-energy-unified-v2`, and confirmation `maintenance-backup-restore`. The workflow confirms maintenance, captures previous-app provenance with a read-only non-admission schema/history snapshot, stops/removes the old app, then requires the full writer-drain and read-only DB identity/history/schema/lock preflight before creating an encrypted backup. It restores the backup and rehearses migrations only on isolated disposable PostgreSQL. Review the report, restore result, artifact, and digests before continuing.
3. Dispatch **Manual production migration** from `main` with the same SHA and manifest and confirmation `MIGRATE_PRODUCTION`. The owner-only signing job binds the exact pending set, source identity, preflight, backup, restore rehearsal, and writer-drain evidence. The execution job rechecks canonical `main`, clean exact checkout, all six committed SQL blobs, migrator image bytes, backup freshness, live DB identity and writer drain. The durable `ddl-started` marker is written immediately before the single Prisma container invocation. It records possible schema uncertainty; it does not prove Prisma started or PostgreSQL received DDL. From this boundary, keep the app stopped and traffic in maintenance until the exact compatible release succeeds or a separately verified pre-DDL restore completes.
4. Prisma runs once with PostgreSQL `lock_timeout=5000`; the script blocks rerunning while the marker exists. Failure leaves the app stopped, Caddy in maintenance, and the marker at `ddl-started`. After success, read-only postflight must match the disposable restore before the marker advances to `schema-applied`.
5. Dispatch **Manual production app deploy** from `main` with the same SHA, confirmation `deploy`, and non-serving mode enabled. The candidate starts only behind maintenance and only when the marker matches its exact SHA and state. Health and immutable image/SHA identity must pass before the marker advances to `app-ready`.
6. Dispatch **Owner-authorized Unified V4 activation and traffic serve** for the same exact current-main SHA with `ACTIVATE_UNIFIED_V4_AND_SERVE`. The workflow checks V3 postflight, explicitly activates/replays V4, checks currentness and coverage, then changes the serving route only if every gate passes.

## Owner-authorized database cutback

The only automated recovery path for a failed DDL release is **Owner-authorized production database cutback** (`production-database-cutback.yml`). It is a separately dispatched workflow, not an automatic migration rollback. Dispatch it from `main` with the exact current-main tooling SHA, the failed production-migration run ID, and `RESTORE_PRE_DDL_DATABASE`. The owner gate verifies actor and triggering-run identity, exact current `main`, successful CI for that SHA, and that the selected migration run is the completed failure for the release. It then verifies the migration's signed authorization, its exact preflight and restore-rehearsal evidence, and the encrypted backup artifact/file digests before the production job receives SSH or backup-encryption credentials.

The workflow decrypts the selected encrypted backup on the runner, checks authenticated backup bytes and that PostgreSQL can read the archive, then transfers the fixed signed evidence bundle and backup stream over pinned SSH. The host cutback script acquires the shared production lock and requires a clean checkout at the exact current-main SHA. It verifies the existing release marker belongs to the failed release, the exact public maintenance response is active, the app container is absent, writer drain is complete, PostgreSQL is healthy, and the live database matches the signed pre-DDL cluster/database identity. It creates a fresh staging database on that same PostgreSQL cluster and restores the archive in one transaction. Before promotion it verifies the restored schema, Prisma migration history and checksums, required data readability/counts, same-cluster identity, and compatibility with the captured previous app provenance and immutable image/runtime configuration.

Pre-DDL app provenance record schema v2 distinguishes `release-sha-v1` from `legacy-unlabeled-v1`. A labeled deployment must retain a full 40-character release SHA; the cutback verifies its restored Prisma history against that SHA's committed migration tree. A legacy image is admitted only when the release-SHA label is genuinely absent. Its source SHA is recorded as `unavailable`, never inferred from a Docker image ID. The record binds the healthy container ID, immutable image ID, runtime-configuration digest, and read-only pre-DDL PostgreSQL identity, migration-history, and schema-inventory digests. The workflow compares those digests with the admitted preflight result before backup; cutback re-verifies the owner-signed preflight evidence and requires the restored database's schema and migration history to match it exactly. Missing, changed, or incomplete evidence blocks promotion.

Immediately before the first destructive database rename, after rechecking the failed-release marker, maintenance route, writer drain, and live DB identity, the host refreshes canonical `origin/main` again. A fetch error or SHA mismatch prevents either rename. After all gates pass, it renames the migrated `bodycast` database to `bodycast_failed_<migration-run-id>` and promotes the restored staging database to `bodycast`. If the second rename fails, the script attempts to return the original migrated database name; it does not run Prisma rollback SQL. The migrated database is retained after a successful promotion.

After promotion, the host verifies the new live target identity and repeats the signed-baseline schema/history and data-readability checks before advancing the marker to `database-restored`. It recreates only the captured immutable image and verifies a new container ID, image ID, exact runtime-configuration digest, and health. A labeled image must reproduce its exact previous SHA label. A legacy-unlabeled image is started with the explicit `unknown` Compose label value, which does not claim a commit SHA; its compatibility instead comes from the verified healthy pre-DDL observation and exact signed pre-DDL schema/history restoration. Any identity or health mismatch leaves maintenance and the marker in place. The host then advances the marker to `rollback-app-ready`, validates the fixed serving route, and rechecks current `main` immediately before atomic route replacement. That replacement is the serving commit. Only after it commits does the workflow attempt Caddy reload, an observational public probe, and marker cleanup. A cleanup failure leaves the marker in place and is reported; it does not undo the committed route.

Ordinary API/container startup and app deploy do not run Prisma migrations or V4 activation/replay. Merge and green CI do not auto-deploy. An active marker blocks an old/mismatched SHA, serving deployment, or migration retry. Do not run `docker compose up app` manually while the marker exists; use the exact-SHA non-serving workflow after the migration has completed.

## Failure and recovery rules

- **Before the marker exists:** migration execution has not crossed its irreversible boundary and this attempt has not spawned Prisma. The schema remains at the prior release. Resolve the preflight/authorization issue; if returning to service, use the reviewed maintenance procedure to restart the prior exact app SHA only after confirming the old schema remains intact. Keep maintenance when writer state is uncertain and never reuse stale writer evidence.
- **After `ddl-started` is written but before or around Prisma spawn:** treat the schema as potentially changed, even if the container did not start, the process exited immediately, or logs show no DDL. Keep the marker, keep the app stopped, and keep Caddy on 503. Process exit, a missing Prisma log, or an operator belief that DDL did not run is not grounds to clear the marker or deploy the old SHA. Diagnose the failure; do not retry migrations in place without a separately reviewed recovery decision.
- **During or after DDL:** treat the database as potentially partially migrated. Keep the marker, app stopped, and Caddy on 503. Preserve the failed database and logs for diagnosis. Do not restart the old image and do not retry migrations in place.
- **After DDL, before the compatible app is healthy:** keep `schema-applied`/`ddl-started` marker and maintenance. Retry only the exact-SHA non-serving app deployment after diagnosing startup; do not repeat Prisma migration. The marker prevents deployment of the prior binary.
- **After the new app starts, before V4 replay:** keep `app-ready` and maintenance. Fix/complete only the explicit V3/V4 rollout path. Forecast V2 traffic remains blocked while currentness or coverage is missing.
- **During V4 replay:** leave Caddy on 503 and preserve the app/marker and database evidence. Resume only through the explicit replay tooling after examining its idempotency/currentness report; do not clear the marker or reopen traffic on partial output.
- **Cutback failure before database promotion:** keep the maintenance route and marker. The script removes its incomplete staging database when safe; it does not start the previous app or alter the migrated database. Preserve workflow logs and the signed artifacts. Do not retry blindly if a staging or failed-run database name already exists.
- **Cutback failure during database promotion:** keep maintenance and the marker, and do not start either app. The script attempts to restore the original migrated database name if staging promotion fails. If that name repair fails or the observed database names are ambiguous, stop and have the owner inspect the PostgreSQL catalog and workflow logs before any further DB command. Do not manually rename/drop databases or edit the marker.
- **Cutback failure after database promotion but before serving commit:** keep maintenance and the marker; the migrated database remains retained as `bodycast_failed_<migration-run-id>`. If the previous app had started, the script disables restart and stops/removes it on failure. Do not start an app until the exact restored database identity and captured previous runtime have been re-verified. Preserve evidence and require owner review before another action.
- **After serving commit:** route replacement is final. Caddy reload, public probe, marker cleanup, or reporting errors do not trigger rollback. If the marker remains, leave it intact and fail closed for subsequent release operations; do not clear it manually. Record the workflow outcome and have the owner review the live route and marker state.
- **Cutback eligibility is not established:** do not improvise a restore. Keep maintenance, app stopped, and marker intact. The workflow requires the exact signed pre-DDL backup and source identity, a successful isolated restore rehearsal, complete matching schema/history evidence, and the captured compatible prior runtime. If the legacy provenance record, image pin, runtime digest, signed baseline, or restored state is absent or disagrees, cutback fails closed and requires operator review before any destructive action.

## Validation and environment separation

Configure and review GitHub environment protection before using the workflows. The tooling does not read or change environment settings or secrets.

| Environment | Workflow purpose | Secret names |
| --- | --- | --- |
| `production` | Maintenance topology, preflight, backup, restore rehearsal | `SSH_PRIVATE_KEY`, `SSH_HOST`, `SSH_USER`, `SSH_PORT`, `SSH_HOST_FINGERPRINT`, `DEPLOY_PATH`, `APP_HOST`, `CADDY_ROUTES_PATH`, `PRODUCTION_BACKUP_ENCRYPTION_KEY` |
| `production-migration-authorization` | Sign authorization only | `PRODUCTION_MIGRATION_SIGNING_KEY_ID`, `PRODUCTION_MIGRATION_ED25519_PRIVATE_KEY` |
| `production` | Final protected execution | `SSH_PRIVATE_KEY`, `SSH_HOST`, `SSH_USER`, `SSH_PORT`, `SSH_HOST_FINGERPRINT`, `DEPLOY_PATH`, `APP_HOST`, `CADDY_ROUTES_PATH` |

The signing key exists only in `production-migration-authorization`; SSH and backup credentials exist only in `production`. The execution job never receives the signing private key, and the signing job never receives production SSH/DB/backup secrets.

Safety CI verifies all six manifest hashes, exact pending sets, migration artifact bytes, Relative Muscle schema signatures, populated legacy-row migration, old `profileId_date` client rejection after migration, writer reconnect/unknown-client/topology blockers, Prisma lock timeout and target identity, plus encrypted backup/restore safety on isolated PostgreSQL. Use only local/CI databases with explicit test identities. Never point these scripts at production except through the separately authorized workflows described above.
